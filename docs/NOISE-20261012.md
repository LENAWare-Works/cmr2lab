## THE SHORT VERSION

He said the game was "a worse state than before, graphics rendering needs serious work".
The claim was backed with speckle deltas of 3.8× and 2.7× between build `4c2998f345c9`
(the 09:27 build he called *amazing*) and build `94ed1359c405` (tonight's).

**Those pairs are not the same moment**, and the deltas are content, not noise:

* the only pair in the published set whose two frames are actually the same picture is the
  main menu at frame 2600, and there the two builds are **identical**: speckle 0.091 % on
  both, ratio **1.000**;
* the "demo, same index" pair differs in **98.6 %** of pixels (78.8 % of them by more than
  8 luma) — two car silhouettes in different places, a displaced road edge, lane markings
  as strokes. See `diff-demo3000-amp4.png` in this directory: that is structure, not grain;
* the control nobody had run: **one and the same binary**, same harness, same frame index,
  two runs (`v2.ppm.5000` vs `fx-b.ppm.5000`, both `4c2998f345c9`) reads
  **speckle 1.493 % vs 0.314 % = 4.76×** — a larger "noise delta" than either reported
  number, with no build difference whatsoever;
* within tonight's build alone, speckle spans **0.021 % → 0.214 % → 1.719 %** across the
  setup screen, the demo and a race. It measures content first and noise second.

So: **no evidence of a noise regression, and no refutation of one either.** What is missing
is a content-matched 3D pair. The published frames are not it, and no pair on disk is it.

## THE NUMBERS

Instrument: `scan-frames.py`. luma = 0.299/0.587/0.114. **speckle** = share of pixels whose
luma differs from **both** horizontal neighbours by ≥ 24 in **opposite** directions (a
single-pixel alternation, i.e. flicker). **div** = mean absolute difference of 64×40 mean-luma
signatures; **differ / >8** = per-pixel census against the other frame.

### The published pairs, and whether the two halves are the same picture

| pair | frame index | differ | > 8 luma | speckle A : B | ratio |
|---|---|---|---|---|---|
| main menu | 2600 : 2600 | **0.046 %** | 0.029 % | 0.091 % : 0.091 % | **1.000** |
| demo | 3000 : 3000 | 98.60 % | 78.84 % | 0.214 % : 0.063 % | 3.4× |
| race | 5500 : 6000 | 98.87 % | 81.13 % | 1.719 % : 0.658 % | 2.6× |

`differ` is the honest content control: the menu pair is the same picture with the
`Time 00:00.28` clock as the only difference. The other two are different moments.

| index | differ | > 8 luma | speckle B : A | ratio |
|---|---|---|---|---|
| 2600 | 0.046 % | 0.029 % | 0.091 : 0.091 | 1.00 |

## WHAT WOULD ACTUALLY SETTLE IT

**1 — In-process A/B of the only code that differs between the two arms.**
The build on the play path, `94ed1359c405`, carries r37's file trigger:
`LENA_ALIGNTRIG=/tmp/alignon` makes the TL-align block run **iff that file exists**, sampled
once per frame, so **adjacent frames render with align ON and OFF inside one process**
(demonstrated in one run by CAR-r38: `align_gate=0 → 1057 frames, align_gate=1 → 630`).
On a **static** 3D frame this is a content-matched A/B with everything but the align block
held fixed. Precondition, cheap: with the trigger held at one value, two consecutive frames
must come out near-identical — if they do not, the screen is not static and the test does not
apply. TL-align is the whole code delta between `4c2998f345c9` (09:27) and `94ed1359c405`
(11:03); the near clip is in both arms and therefore cannot explain a delta.

**2 — A matched cross-build pair, if the screen will not hold still.**
The first 3D frame is deterministic across runs: `RACE/out` witnesses
`fx-race.witness.000/.001` and `fx-d.zline.ppm.000/.001` are **md5-identical**
(`c0f928fe…`, `39525397…`) from two different runs and two different scripts on the same
build. So running each arm with `LENA_ZLINE_SNAP` gives a content-matched pair at the
stage-load instant for ~6 minutes and no keys per arm (`gpu-guard` first, always).

**Do not do this by comparing attract-demo frames at equal indices.** That is what produced
the two numbers this page exists to correct.

## THE RULE THAT CAUSED THE CONFUSION, IN ONE LINE

A screenshot is evidence only if the binary behind it is named and the moment in the other
frame is the same moment. On 2026-10-12 the binary under the icon changed eight times between
17:53 and 20:19 (`work/PLAY/out-plain/.lre-buildlog`) and was never announced, so neither
"before" nor "after" could be pinned. From now, a build that lands on that path is a
handover: one at a time, with its gate attached, never while a game is alive — see
`docs/NOISE-20261012.md`, `work/tools/play-handover.sh` and §4 of `work/ROUND-DISCIPLINE.md`.
